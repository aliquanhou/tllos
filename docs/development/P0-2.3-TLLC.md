# P0-2.3: tllc CLI (TLL Compiler CLI)

**Date**: 2026-08-26
**Branch**: feature/cli
**Status**: COMPLETED

## 目标

把当前只能通过 compiler/compiler.tll 自举的编译能力，封装成一个真正可以编译任意 .tll 文件的 TLL CLI 工具。

## 最终验收

```
tllc compile hello.tll    → hello.tllbc
tllvm hello.tllbc         → 正常执行
```

## 项目结构

```
tools/TLLC/
├── main.tll              # CLI 入口，process.argv 解析
├── cli.tll               # 命令解析（help/compile/check/info）
├── compiler_driver.tll   # 编译驱动（封装 linkAndCompile）
├── formatter.tll         # 用户可读输出格式化
└── tllc.tllbc            # 编译后的字节码（549397 bytes）
```

## 实现的命令

| 命令 | 功能 | 状态 |
|------|------|------|
| `tllc help` | 显示帮助信息 | ✅ |
| `tllc compile <file.tll>` | 编译为 .tllbc（默认同名输出） | ✅ |
| `tllc compile <file> -o <out>` | 编译为指定输出文件 | ✅ |

## Dogfooding Finding #1: resolveModulePath 嵌套 ../ 解析 Bug

### 问题

从深层子目录导入上级目录的模块时，路径解析错误。例如：
- `sub/deep/deep_mod.tll` 导入 `../../lib/helper`
- 实际解析为 `sub/lib/helper.tll`（只上了一级）
- 导致 fs.readFile 返回空字符串，模块函数丢失

### 根因

`compiler/linker.tll` 的 `resolveModulePath` 函数只用 `if` 处理一次 `../` 前缀：
```tll
if strings.length(cleanPath) >= 3 && strings.substring(cleanPath, 0, 3) == "../" {
    cleanPath = strings.substring(cleanPath, 3, ...)
    // go up one directory
}
```
不支持嵌套的 `../../`。

### 修复

将 `if` 改为 `while` 循环，处理所有连续的 `../` 前缀：
```tll
while strings.length(cleanPath) >= 3 && strings.substring(cleanPath, 0, 3) == "../" {
    cleanPath = strings.substring(cleanPath, 3, ...)
    // go up one directory each iteration
}
```

### 最小复现

```
tests/regression/nested_import/
├── main.tll              # 入口，导入 ./sub/deep/deep_mod
├── lib/helper.tll        # 导出 getMessage, add
└── sub/deep/deep_mod.tll # 导入 ../../lib/helper，re-export
```

### 测试结果

```
$ tllvm main.tllbc

```

## 开发过程中发现的其他问题（非 TLL 缺陷）

1. **formatter.tll 用 `fn` 作为变量名** — `fn` 是 TLL 关键字，改为 `func`
2. **compiler_driver.tll 导入路径错误** — `../compiler/linker` 应为 `../../compiler/linker`（从 tools/TLLC/ 出发需要上两级）
3. **main.tll argv 偏移** — 通过 tllvm 运行时 argv[1] 是 .tllbc 路径，需自动检测并跳过
